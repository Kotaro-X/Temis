# ギルド機能 仕様書（実装依頼用）

- 状態: Draft v0.1
- 対象: WeMemo モバイルアプリ
- 実装対象: 投稿・発見機能「ギルド」およびプロジェクト参加／スカウト導線
- 実装対象外: 本書の作成時点では既存コードの変更を行わない

## 1. 背景と目的

WeMemo 内の個人の探究やプロジェクト活動を、他ユーザーが発見できるようにする。
ユーザーはメモを任意で「ギルド」に投稿し、無限フィードとタグ検索から関心の近い探究を見つける。投稿をきっかけに、ユーザー同士のつながり、公開プロジェクトへの参加、プロジェクトからのスカウトを生む。

本機能の目的は、次の二つである。

1. 個人の探究を外部へひらき、関心・技能が近いユーザー同士の接続を生む。
2. プロジェクトの活動と参加者を増やし、継続的な共同活動を生む。

## 2. 用語

| 用語 | 定義 |
| --- | --- |
| ギルド | WeMemo の投稿・発見機能全体の名称。プロジェクトそのものを指さない。 |
| 投稿 | ギルドのフィードに表示する公開コンテンツ。個人メモまたはプロジェクト内メモを元に作成する。 |
| 元メモ | 投稿作成時に参照する個人メモまたはプロジェクトメモ。既存の作業・思考の原本。 |
| 公開プロジェクト | 概要とギルド投稿を一般ユーザーが閲覧でき、参加申請を受け付けるプロジェクト。 |
| つながり | ユーザー間の相互承認済みの関係。既存の接続モデルを利用する。 |
| スカウト | 投稿者を、スカウト送信者が権限を持つプロジェクトへ招待すること。 |

## 3. プロダクト原則

- ギルドは、探究を発見して共同活動につなげる無限フィードである。単なる閲覧・反応数の競争を主目的にしない。
- 元メモは常にプライベートを既定とし、投稿操作をした場合にのみ公開される。
- 投稿は元メモとは別の公開用データとして保持する。元メモの非公開性、編集履歴、削除を投稿表示と混同しない。
- 投稿者はいつでも投稿を編集、非公開化、削除できる。
- 投稿から行える主要な行動は「つながり申請」「プロジェクト参加申請」「プロジェクトへスカウト」である。

## 4. ナビゲーション

### 4.1 入口

- Private ワークスペースを開いている時だけ、画面下部のタブバーに `ギルド` タブを表示する。
- Private の下部タブ順は `タスク / Todo / メモ / ギルド` とする。
- Projects ワークスペースではギルドタブを表示しない。プロジェクト内では、各メモから「ギルドに投稿」の導線を利用する。
- ギルドタブを開くと、前回のタグフィルタとスクロール位置を保持したフィードへ戻る。

### 4.2 ギルド画面の構成

画面は以下の順で構成する。

1. ヘッダー: `ギルド`、投稿作成ボタン
2. フィード切替: `おすすめ` / `新着` / `つながり・参加中`
3. 横スクロールのタグフィルタ
4. 無限スクロールの投稿フィード
5. 空状態または読み込み・エラー状態

初期リリースでは、`おすすめ` はユーザーの興味タグとフォロー・参加状態を用いた軽量な並び替えでよい。推薦モデルや外部AIによるランキングは含めない。

## 5. 投稿仕様

### 5.1 投稿できる人・元データ

- ログイン済みユーザーのみ投稿できる。
- 投稿作成の入口は、次の二つとする。
  - Private のメモ詳細: `ギルドに投稿`
  - プロジェクト内のメモ詳細: `ギルドに投稿`
- 新規投稿をギルド画面から作成する場合も、公開用本文を入力した後に元メモを作成または関連付ける。
- プロジェクト内メモを投稿するには、そのプロジェクトでメモを作成・編集できる権限が必要である。

### 5.2 公開範囲

投稿の公開範囲は、初期リリースでは `公開` のみとする。

- 公開: ログイン済みの全ユーザーがギルドのフィード、タグフィルタ、投稿詳細から閲覧できる。
- 下書き: 投稿作成中のみ。フィードには表示しない。
- 非公開化: 公開済み投稿をフィードと検索対象から直ちに外す。投稿データは投稿者のみ復元または削除できる状態にする。

`つながりのみ` の公開範囲、外部Web公開、匿名投稿は初期リリースに含めない。

### 5.3 投稿内容

投稿は以下を持つ。

| 項目 | 必須 | 仕様 |
| --- | --- | --- |
| 投稿ID | 必須 | 一意なID。 |
| 投稿者ID | 必須 | 投稿を作成したユーザー。 |
| 投稿者表示名・画像 | 必須 | フィード表示用スナップショット。プロフィール非公開化後も投稿者が表示名を変更できること。 |
| 投稿本文 | 必須 | 元メモから選択・編集した公開用本文。最大文字数は既存メモの上限と整合させる。 |
| タグ | 必須 | 1〜5件。正規化済みタグ文字列。 |
| 投稿種別 | 必須 | `personal`、`project_activity`、`project_recruiting`。 |
| 関連プロジェクトID | 条件付き必須 | `project_activity` と `project_recruiting` では必須。`personal` では任意。 |
| 元メモ参照 | 任意 | 元メモの種別とID。公開API・フィードには返さない。 |
| 公開状態 | 必須 | `published`、`unpublished`、`deleted`。 |
| 作成・更新日時 | 必須 | フィード順・ページングに使用する。 |

- 元メモの本文をそのまま共有せず、投稿保存時の公開用本文を保存する。
- 投稿本文を編集しても元メモは更新しない。
- 元メモを削除しても、投稿の公開用本文は自動削除しない。ただし投稿者には「元メモは削除済み」と分かる管理表示を出す。
- 投稿の削除は論理削除とし、通常のフィード・検索結果・詳細から除外する。

### 5.4 投稿フォーム

投稿前に以下を明示的に確認させる。

- 公開する本文
- 付与するタグ
- 投稿種別
- 関連プロジェクト（任意または必須）
- プロジェクト名・募集内容が全ユーザーに表示されること

プロジェクト内メモを元にする場合も、自動公開はしない。必ず投稿フォームを経由する。

## 6. フィードとタグフィルタ

### 6.1 フィード

- 投稿は無限スクロールで追加読み込みする。
- デフォルトは `おすすめ`。初期実装では以下の順で優先する。
  1. 選択済みタグに一致する投稿
  2. 自分の興味タグに一致する投稿
  3. つながりのある投稿者、または参加中プロジェクトの投稿
  4. 上記以外の新着投稿
- `新着` は公開日時の降順とする。
- `つながり・参加中` は、つながりのある投稿者または自分が参加するプロジェクトに関連する投稿のみを、新着順で表示する。
- 同じ投稿を同一のフィードセッションで重複表示しない。
- 投稿を非公開化・削除・ブロックした場合は、次回取得時からフィードに出さない。

### 6.2 タグ

- ユーザーはタグを複数選択できる。
- 複数選択時は OR 条件とする。例: `#AI` と `#教育` を選ぶと、いずれかを含む投稿を表示する。
- 選択中タグはフィードの優先順位と取得条件の両方に適用する。
- `すべて` を選ぶとタグフィルタを解除する。
- タグは投稿時に新規作成できるが、表記揺れを抑えるため、小文字化・前後空白の除去・文字数制限を行う。
- タグ管理や AND 条件、人気タグランキングは初期リリースの対象外とする。

### 6.3 ページングと更新

- カーソルベースで取得する。オフセットページングは使用しない。
- 初回取得、追加読み込み、下方向プル更新を区別する。
- タグ・フィード種別の変更時は、既存の結果とカーソルを破棄して先頭から取得する。
- 追加読み込みの失敗は、既存表示を消さず、再試行ボタンを表示する。

## 7. 投稿詳細とアクション

投稿詳細には、投稿本文、タグ、投稿者、関連プロジェクト、主要アクションを表示する。

### 7.1 投稿者へのつながり

- 自分以外の投稿者には `つながり申請` を表示する。
- 既に申請中の場合は `申請済み`、接続済みの場合は `つながり済み` を表示する。
- 投稿者が申請を無効化している、または投稿者が閲覧者をブロックしている場合はボタンを表示しない。
- 初期リリースでは、投稿へのコメント・DM・リポストは実装しない。

### 7.2 プロジェクト参加申請

以下をすべて満たす場合、関連プロジェクト欄に `参加を申請` を表示する。

- 投稿に関連プロジェクトがある。
- プロジェクトが公開状態である。
- プロジェクトの参加ポリシーが申請受付である。
- 閲覧者が未参加であり、申請中でもない。

申請フォームでは、希望ロール（初期値: member）と任意のメッセージを入力できる。申請先プロジェクトのオーナーが承認または却下する。

承認時には、プロジェクトメンバー情報とユーザー自身が読めるプロジェクト参加インデックスを、同一の原子的処理で作成する。

### 7.3 スカウト

- 投稿詳細で、自分が招待権限を持つプロジェクトが1件以上ある場合に `プロジェクトへスカウト` を表示する。
- スカウト送信者は招待先プロジェクトを1件選び、任意のメッセージを付けて招待する。
- 既存のプロジェクト招待と同じ承認フローを使用する。
- 投稿者が接続申請を無効化している場合でも、スカウト受信の可否は独立した設定として将来追加できるようにする。初期リリースではスカウトを受信可能なユーザーに限定しない。

## 8. 公開プロジェクト仕様

プロジェクトとギルドは別概念である。公開プロジェクトは、ギルド投稿の関連先・参加申請先として扱う。

### 8.1 公開設定

- オーナーはプロジェクトの公開設定を `非公開` または `公開` に変更できる。
- 公開プロジェクトは、名前、説明、アイコン、タグ、公開されている関連投稿を閲覧できる。
- 公開設定だけでは、プロジェクト内メモ・タスク・メンバー一覧を閲覧可能にしてはならない。
- プロジェクト内メモは、投稿フォームを通じて公開した投稿だけが外部から見える。

### 8.2 参加ポリシー

- 初期リリースの公開プロジェクトは `承認制` のみとする。
- `即時参加` は実装しない。
- オーナーは参加申請を承認・却下できる。
- 承認済みユーザーは初期値で `member` とする。`viewer` はオーナーが後から変更できる。
- プロジェクトを非公開へ戻しても、既存メンバーは保持する。保留中の参加申請はオーナーが明示的に処理するまで保留とする。

## 9. 権限・安全性・モデレーション

### 9.1 読み書き権限

- ログイン済みユーザーのみギルドを閲覧・投稿できる。
- 投稿者だけが自分の投稿を編集、非公開化、削除できる。
- プロジェクト投稿を作成できるのは、そのプロジェクトの投稿作成権限を持つメンバーだけである。
- 投稿の公開状態や関連プロジェクトを、クライアントの表示制御だけで保護してはならない。データ取得・更新の認可ルールでも検証する。
- 参加申請の作成者、対象プロジェクト、対象ユーザー、申請状態の遷移をサーバー側ルールで検証する。

### 9.2 ブロック・通報

- ブロック済みの相手の投稿はフィード、検索、投稿詳細から除外する。
- ブロック中は、つながり申請、参加申請経由の接触、スカウトを許可しない。
- 各投稿に `通報` を置き、対象投稿、通報者、理由、作成日時を記録する。
- 投稿者は自分の投稿を削除できる。管理者は通報済み投稿を非表示にできる設計とする。
- メモ本文、Privateのタスク、非公開プロジェクトのメタデータをテレメトリやエラー記録へ送らない。

### 9.3 レート制限

初期値は実装時に調整可能な設定として持つ。

- 投稿作成: 1ユーザーあたり1日20件まで
- つながり申請: 1ユーザーあたり1日30件まで
- プロジェクト参加申請: 1ユーザーあたり1日10件まで
- スカウト: 1ユーザーあたり1日20件まで

制限到達時は、理由と次に送信できる目安を表示する。

## 10. データモデル（論理設計）

### 10.1 GuildPost

```ts
type GuildPostType = "personal" | "project_activity" | "project_recruiting";
type GuildPostStatus = "published" | "unpublished" | "deleted";

type GuildPost = {
  id: string;
  authorUserId: string;
  authorDisplayName: string;
  authorPhotoUrl: string | null;
  body: string;
  tags: string[];
  type: GuildPostType;
  projectId: string | null;
  source: { scope: "personal" | "project"; memoId: string } | null;
  status: GuildPostStatus;
  createdAt: number;
  updatedAt: number;
  publishedAt: number | null;
};
```

### 10.2 ProjectJoinRequest

```ts
type ProjectJoinRequestStatus = "pending" | "accepted" | "declined" | "withdrawn" | "cancelled";

type ProjectJoinRequest = {
  id: string;
  projectId: string;
  applicantUserId: string;
  requestedRole: "member" | "viewer";
  message: string | null;
  status: ProjectJoinRequestStatus;
  reviewedByUserId: string | null;
  reviewedAt: number | null;
  createdAt: number;
  updatedAt: number;
};
```

### 10.3 堅持するデータ分離

- `GuildPost.body` は公開用本文であり、Privateメモの本文フィールドを直接参照するビューにしない。
- `GuildPost.source` は投稿者の管理・投稿解除用であり、他ユーザーへの返却データには含めない。
- 公開プロジェクトのメンバー専用メモ・タスクは、既存の参加メンバー認可を維持する。
- 投稿の表示名・画像はフィード描画を安定させるためスナップショットを持つ。ただし本人が表示名を変更した場合に同期する方針は実装時に統一する。

## 11. 状態遷移

### 11.1 投稿

```text
下書き → 公開 → 非公開 → 公開
              └→ 削除
非公開 → 削除
```

- 削除済み投稿は通常の画面では復元できない。
- 非公開化は公開解除であり、投稿者だけが再公開または削除できる。

### 11.2 参加申請

```text
申請中 → 承認 → プロジェクトmember
      ├→ 却下
      └→ 申請者が取り下げ
```

- 同じプロジェクトに対する申請中レコードは、ユーザーごとに最大1件とする。
- 承認済みメンバーは改めて参加申請できない。

## 12. 画面別の受け入れ条件

### 12.1 Private下部タブ

- Privateワークスペースでは下部タブに `ギルド` が表示される。
- Projectsワークスペースでは `ギルド` タブを表示しない。
- ギルドタブ選択中は他タブと同じ選択状態・安全領域・画面遷移規則を満たす。

### 12.2 フィード

- 初回表示時に公開済み投稿だけが表示される。
- 追加読み込みにより、重複なく次ページを表示できる。
- タグを1件以上選択すると、選択タグのいずれかを持つ投稿だけが表示される。
- フィルタ解除で全投稿のフィードへ戻る。
- 空状態は「タグに合う投稿がまだありません」と、フィルタ解除または投稿作成の導線を示す。

### 12.3 投稿作成・管理

- Privateメモおよびプロジェクトメモから、明示操作で投稿フォームを開ける。
- 元メモの保存だけでは投稿が公開されない。
- 投稿を非公開化すると、次回のフィード取得・タグ検索・投稿詳細から閲覧できない。
- 投稿を編集しても元メモ本文は変わらない。

### 12.4 接続・プロジェクト導線

- 未接続の投稿者へつながり申請を送信でき、送信後は重複送信できない。
- 公開・承認制プロジェクトに対して、未参加ユーザーは参加申請を送信できる。
- オーナーが参加申請を承認すると、申請者がプロジェクトを開ける。
- 招待権限を持つユーザーは投稿者を自分のプロジェクトにスカウトできる。
- ブロック済み関係では、相互の投稿閲覧と接触アクションができない。

## 13. 計測指標

投稿数や閲覧数だけでなく、探究から共同活動への遷移を測る。

| 指標 | 定義 |
| --- | --- |
| 投稿起点の接続率 | 投稿閲覧後7日以内に、つながり申請・参加申請・スカウトのいずれかが発生した投稿の割合。 |
| 参加申請承認率 | 参加申請のうち承認された割合。 |
| 共同活動化率 | 参加承認後7日以内に、承認者が対象プロジェクトでメモまたはタスクを作成した割合。 |
| 投稿者継続率 | 初回投稿者のうち、翌週にも投稿またはプロジェクト活動を行った割合。 |
| タグ発見率 | タグフィルタ使用セッションのうち、投稿詳細の閲覧または接続アクションに至った割合。 |

計測イベントには投稿本文、メモ本文、プロフィール本文、検索語を含めない。

## 14. 初期リリースの対象外

- コメント、DM、引用投稿、リポスト
- いいね数・フォロワー数を競わせるランキング
- 外部Webから閲覧できる公開プロフィール／投稿
- 動画・音声・大容量ファイルの投稿
- AIによる推薦、モデレーションの自動判定
- 公開範囲 `つながりのみ`
- プロジェクトへの即時参加
- 人気順、AND検索、トレンドタグ

## 15. 実装開始前に確定が必要な事項

1. 投稿本文、画像、タグ名の上限値。
2. 画像投稿を初期リリースに含めるか。含める場合の保存先・容量・削除仕様。
3. `おすすめ` の初期並び替えを、完全な新着順にするか、興味タグを優先するか。
4. 投稿者がプロフィールを非公開に変更した場合、既存の公開投稿を維持するか非公開化するか。
5. 元メモが削除された投稿を、投稿者が継続公開できるか。
6. スカウト受信をユーザー設定で拒否できるようにする時期。
7. 通報の確認・投稿非表示を誰がどの運用で行うか。

## 16. 実装時の作業分解（参考）

1. ギルド用の型、Firestoreデータモデル、認可ルール、インデックス、テストを追加する。
